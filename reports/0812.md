# Robot experiments on the NVS-SGG framework

Written 12 August.  Three things had been run: an oracle pointer with motion, the
paper's A+C+R fusion applied to an instruction without motion, and the tabletop
generator that replaced the iTHOR scenes.  Sections 1 and 2 are on the iTHOR
line, which section 3 supersedes; they are kept for the findings that still bind
and trimmed of everything else.

**Motion is covered by `0821.md`, not here.**  The walk described in section 3
used a bearing rule and a stop rule that have both since been replaced.

---

# 1. Oracle pointer, with motion (retired)

59 `on` tasks, up to 10 moves, three policies (`stay` / `random` / `nvs`) sharing
one grader and one budget.  It walked to the pose of the best RECOVERING view,
which means `grounded_rank` -- THOR's own box -- was inside the control loop, so
no result from it transfers to a robot.  Retired for that reason;
`eval_nvs_loop.py` is in `archive/`.

The one finding worth carrying: motion had no effect on whether the task was
solved (p = 0.61) and a decisive effect on how fast (12-0, p = 0.0002).  Choosing
a viewpoint was already worth something before any of the fusion work.

# 2. A+C+R applied to an instruction, no motion (current)

The fusion the paper ships (`lib/fusion/channels.py`, channels A+C+R) run on a
live THOR frame plus 20 synthesised views, asked an instruction instead of a
benchmark. `fuse_live.py` imports the paper's own functions rather than
reimplementing them, and `--beta 0` reproduces `sgg_live.predict` exactly, which
is checked every run (71/71 passed).

71 cases across 28 floor plans, `Find the bottle behind the plant`, occluder
staged to hide the landmark by a median 36% (band 0.25–0.50).

| | source |
|---|---|
| the two class names and the predicate | **the instruction** |
| which query is the bottle, which is the plant, how strongly they relate | **the model** |
| which bottle is *the* bottle | **ground truth, at grading only** |

Candidates are the top-10 of EGTR's 200 decoder queries by `p(bottle)` × the
top-10 by `p(plant)` — about 100 pairs. Ranked by `p(class)`, not by argmax
class: median `p(class)` on these targets is 0.07, and requiring argmax would
discard most of the detections. The **predicate is not conditioned**: whether
the model says `behind` about that pair is the quantity under test.

**Robot criterion.** The robot scans the ranked list, takes the *first* entry
matching the instruction, and walks there. Success = that entry is the right
instance (`class_rank == grounded_rank`). A right answer sitting below a wrong
one is a failure, because the robot never gets there.

## Result

| | robot succeeds | instruction matched at all | @1 / @5 / @10 |
|---|---|---|---|
| single-view | 16/71 (23%) | 54 | 1 / 6 / 11 |
| A | 17/71 (24%) | 54 | 1 / 7 / 11 |
| **A+C+R** | **19/71 (27%)** | **59** | 1 / 9 / 15 |

`@K` means "the robot reads only the first K entries of the CONDITIONED list" —
the ~100 pairs the instruction's class names licensed — so the 27% column is
`@100`, the whole list. **This is not the paper's `R@K`**, which ranks against
every triplet in the scene; being 10th out of 100 pairs already known to be
bottles and plants is a far easier bar.

Paired: single → A+C+R gains 5, loses 2. **Not significant** — a 5-vs-2 sign
test is p ≈ 0.23. The honest reading is "no harm, trend upward", not "it works".
**A is worth +1**; C+R the rest, and R's consensus relabel is why "matched at
all" moves 54 → 59. That is the only place multi-view evidence is visibly doing
something.

## The binding constraint is instance disambiguation, not the relation

The first instruction-matching entry sits at a **median rank of 12** (1–74).
59 of 71 cases have the model saying `bottle behind plant` somewhere; only 19
say it about the right bottle, and `@1` is **1**.

The IoU distribution says the threshold is not the argument: successes have a
median best IoU of **0.83**, failures **0.03**. Failures are not near misses —
the box is on a different object. Only 5 of 40 sit in 0.3–0.5.

# Three dead ends, all measured

**`on` is the wrong predicate to test a multi-view mechanism on.** It is
viewpoint-INVARIANT; `channels.py` argues only viewpoint-dependent facts can be
informed by a second viewpoint, and ships predCond with `on` excluded. On 59
`on` cases A+C+R moved the answered count 6 → 6.

**Free-form SGDet has no measurable signal here.** On the same 71 `behind`
cases without conditioning, the instructed triplet reached the top-100 in
**1 of 71** — not because the objects are missing: `probe_size.py` finds EGTR
detects and correctly classifies the target in **31 of 71**. The object end is
fine; the triplet loses the ranking to `laptop on table`. Conditioning on the
instruction's class pair is what turned 1 into 59.

**Target size is not the problem.** The graded instance covers a median 0.55% of
the frame and detection does not fall with size (42% under 0.5%, 53% at
0.5–1%). An earlier reading of the task sheets blamed the standoff distance; the
measurement does not support it.

# Where the robot experiment goes next

The motion loop ran (`eval_move.py`, 71 cases, K=3) and the evidence arm LOST to
the random one: 8 correct against 7, paired 1-vs-6, 17 false stops against 12.
The plots and the stop frames say the cause is not the direction signal itself
but three things underneath it, and the fix for all three is a different kind of
scene rather than a better bearing.

**The relation was doing no work.** All 71 iTHOR cases had ZERO same-class
distractors, so `the bottle behind the plant` and `any bottle` were the same
instruction. Nothing that reads relations could have helped, and the false stops
confirm it: the robot walked to a faucet and a paper-towel roll, the two most
bottle-shaped things in the frame.

**Both arms orbited a bad anchor.** P-hat came from the object-class detection
plus real depth and landed a median 0.48 m from the landmark, worst case 2.28 m.
The arc turns about that point and the camera aims at it, so when it is wrong
both arms look at the wrong place -- and the evidence arm, being consistent,
follows the error more faithfully than the random one does.

**The action space collapsed.** Every step is an arc at a fixed radius about
P-hat, so different bearings walk the SAME circle and the two arms' routes
overlap; the plotted paths show them nearly coincident. Median displacement was
0.29 m for evidence against 0.36 m for random -- the arms were not going to
different places.

# 3. The tabletop dataset, and what it exposed

The generator is `build_tabletop.py`; 40 cases in `nvs_pilot/cases_tabletop.json`.
Every property the experiment needs is now set rather than found: two identical
copies of the target, the occluder bisected to 26-35% of the target, the twin
placed AT THE OCCLUDER'S OWN DEPTH so exactly one copy is behind the landmark.

Four generator faults were found by looking at pictures, and each had been
invisible in the numbers:

- **Objects sank into the table.** `SpawnAsset` positions the PIVOT, which is at
  the centre of the bounding box for some assets and at the base for others, and
  a procedural spawn takes no gravity pass. `Box_10` sat 27 cm into the wood.
  All twelve affected assets were `Box`/`Bread`/`Apple`/`Lettuce` -- exactly the
  `food`/`fruit`/`vegetable` classes an earlier probe had written off as
  undetectable. `proc_scene.place_on` measures and lifts.
- **The camera collided with the table** at the closer standoff, and `one_case`
  caught the exception and moved on, so half the attempts were silently
  rejected and the survivors were systematically the far ones -- undoing the
  change that had just been made to enlarge the targets. `look_from(force=)`
  now separates placing a camera from moving a robot.
- **Both copies were behind the occluder**, because they shared a depth. Fixed by
  construction, not by rejection.
- **The occluder could wander over the table's edge**; `on_table` uses the
  axis-aligned box with a margin, since the table is round and that box is not.

## The detection floor was a measurement artefact

`probe_tabletop.py` reported 12/40 targets detected and wrote off six classes. It
was asking whether the ARGMAX over the query's class distribution equalled the
instructed class. Nothing in this pipeline uses the argmax: conditioning sorts
all 200 queries by p(class) and takes the top N. Asked that way:

```
                   localized   rank median   top10   top20   top40
 target (subject)     40/40         2        30/40   32/40   35/40
 landmark (object)    40/40         2        36/40   38/40   38/40
```

Every object in every case has a query covering it at IoU >= 0.5. EGTR calls a
laptop "box" and an aubergine "banana" while still ranking them first for their
true class. `--condition 10` was discarding a quarter of the targets before the
fusion began; 40 is the operating point.

## The sweep was orbiting a detection, and sometimes a wall

`fuse_live` centred the lemniscate on the 3D point of EGTR's best box for the
LANDMARK class. The trajectory is supposed to be given -- a lookat distance and
a camera path, as `nvs_lemniscate.main` does it. On cases whose landmark is a
`clock` the anchor box landed on the wall, so twenty views orbited a point behind
the room and rendered tiles. The tell was that views 9 and 19, which are the
lemniscate's duplicates of the reference pose, did not look like the reference.
`nvs_lemniscate.orbit_centre` now returns a point `LOOKAT_DIST` down the optical
axis, and all four call sites use it. Every fusion number computed before this
described a broken sweep. See `show_views.py`.

## Result, and where it actually fails

40 cases, `--condition 40 --beta 0`, on the robot's top-1 decision:

```
  pool=max    single 14/40   A 13/40   A+C+R 13/40    A moved the pair UP 4, DOWN 11
  pool=mean   single 14/40   A 14/40   A+C+R 14/40    A moved the pair UP 4, DOWN  9
```

`max` pooling rewards the NUMBER of views a slot corresponds in, and the occluded
target corresponds in 32% of views against its unoccluded twin's 56%, so the
target loses relative ground. `mean` removes the harm. Neither buys a gain.

The two headline counters measure different things and disagree loudly.
`robot succeeds` requires a triplet that literally says `behind` with both
classes right -- 1/40, because EGTR says `on`/`under`/`in` about tabletop pairs
and almost never `behind`. The top-1 decision does not require the model to utter
the word, only to score the right pair highest, and that is the number above.

Where the top-1 pick lands, with both endpoints resolved:

```
   subject on   object on      n
   landmark     nothing       11
   target       landmark      10   correct
   target       nothing        4
   nothing      landmark       4
   twin         landmark       3   the disambiguation this dataset was built for
```

**Candidates are selected by p(instructed class) and scored by `s`, the maximum
over ALL classes.** A box confidently labelled something irrelevant carries a
higher `s` than the target box carries for its own class, so the product
`rel * s_i * s_j` prefers pairs of confidently-mislabelled boxes. That is the 11.
Two other explanations were tested and refuted: the pairs are not degenerate
self-pairs (median box IoU between the chosen endpoints is 0.10), and channel C
cannot merge them because `slot_groups_xyxy` requires the same argmax class,
which is precisely what these two queries do not share.

Scoring by `p_i(subject_class) * p_j(object_class)` instead was tried: the
`landmark behind nothing` bucket fell 11 to 8, but top-1 fell 14 to 13 and a new
failure appeared (`twin behind target`, 4). The errors moved rather than went,
and all three arms then coincide, because the class score contains no `s` for A
to repair. Kept as a flag, not the default.

## Two metrics, and the one we settled on

The two headline counters disagree because they ask different questions, and
under conditioning they run on the SAME 100 candidate pairs:

  `top-1 decision`  the predicate is fixed to the instruction's, and the pair
                    with the highest `rel[i, j, behind]` wins. The model never
                    has to utter the word.
  `robot succeeds`  each pair carries its own argmax predicate -- which R may
                    relabel -- and the first pair LABELLED `behind` wins.

The second is the metric, by decision: the instruction gives the classes but the
relation is what the model has to get right, and R is the channel that acts on
it. Success = that one pair has its subject box on the instructed copy and its
object box on the landmark.

The first was a dead end for the fusion, and the second nearly was for a
different reason. EGTR does not label the true pair `behind` in ANY vocabulary:
argmax over all 50 gives `on` 13, `in` 11, `near` 5, `in front of` 3; restricted
to the seven spatial predicates, or to six with `in` dropped, `behind` is first
in 0 of 40 and sits at median rank 4 of 6. The converse phrasing is no better --
`landmark in front of target` also wins 9 times and discriminates the right copy
in 24/40 against the `behind` field's 28/40. Vocabulary masking cannot fix a
predicate head that does not represent depth order for tabletop pairs.

What survives is that the `behind` FIELD still discriminates:
`rel[target, landmark, behind] > rel[twin, landmark, behind]` in 28 of 40, 70%
against a 50% chance. That is the ceiling the ranking has to realise.

## Result

40 cases, `--condition 10 --topk 100 --beta 0 --objscore mean --rank-by
instructed`, graded at both endpoints:

```
  arm       behind emitted   a correct one exists   and it is first
  single         13/40              4/40                 3/40
  A              13/40              4/40                 3/40
  A+C+R          26/40             10/40                 6/40
```

A alone is single to the case. The whole gain is R, which doubles how often
`behind` is emitted at all. Two losses remain: 26 to 10, R labels the wrong
pair; 10 to 6, a wrong `behind` outranks the right one.

Two settings were worth a point each and both are now defaults. `--topk 10` cut
the list to a tenth of the candidates and was never the protocol -- the iTHOR
runs used 100 -- and ordering the conditioned pairs by `max_p rel` settled which
of two `behind` triplets came first by comparing their `on` scores;
`--rank-by instructed` orders them by the quantity asked about.

## The robot moves

`eval_move.py` on the same 40 cases, three steps, `--trust 10`. The robot looks
with one real frame, and only if that fails does it pay for a sweep and walk.

```
  6 of 40 stopped at the start (1 correct).  Of the 34 that had to walk:
             stopped   both ends correct   subject only   false stops   median m
  evidence      15             3                5              12        0.45
  random        10             0                1              10        —
```

The guided arm wins under either criterion. The false-stop rate is the real
result: the robot stops when a `behind`-labelled pair appears in its own top 10,
and that rule has no notion of confidence -- being behind something is common,
and the twin, a junk box and the landmark itself all satisfy it. Stop ranks are
1 to 6, so this is not the robot believing a deep match.

Of the 15 evidence stops, the subject IoU is bimodal: 5 at or above 0.5, one at
0.46, and 9 below 0.1. It either finds the object or is nowhere near it.

POSES ARE COLLISION-CHECKED. An earlier version forced every teleport and merely
counted the collisions; on the first twelve cases 100% of the steps collided in
five of them, because the START pose was illegal -- the generator had forced it
too. `build_tabletop.stand_back` now accepts only a standoff THOR permits
unforced, `rebuild` no longer forces, and `Robot.teleport` refuses a blocked
destination. Putting the target on the table's NEAR half rather than its centre
made the legal poses CLOSER, so targets grew as well: 0.65% of the frame in
pixels, 1.36% by box, against 0.35%/0.89% before.

# Limits to carry into any write-up

- **Not comparable to the paper's SGDet tables.** Conditioning on the class pair
  is a different question asked of the same model.
- **The NVS is an oracle** — 20 views rendered by THOR, not generated by the
  model. This is an upper bound on what a perfect synthesiser would buy.
- **R is ported, not imported** — it is inline in `occlusion_channels.py` rather
  than a function in `channels.py`, so this copy can drift from it.
- Channel **B is off** by request; **D** is not part of A+C+R. On the tabletop
  metric B is the only channel that could still act -- the decision turns on
  `rel[i, j, behind]`, which A, C and R all leave alone -- so "A+C+R does not
  help the robot choose" is a statement about three channels, not about fusion.
- **The tabletop grading has no amodal box.** `visible_box` reads the
  segmentation frame, so a 35%-occluded target is graded on the part that shows;
  the iTHOR path takes `max(amodal, visible)`. One motion stop failed at IoU
  0.46 for this reason alone.

# Reproducing

The iTHOR line is retired and its commands are in the git history.  The tabletop
line:

```
python build_tabletop.py --n 40 --seed 1 --out nvs_pilot/cases_tabletop.json
python show_tasks.py --cases nvs_pilot/cases_tabletop.json --n 6   # what it asks
python show_views.py --cases nvs_pilot/cases_tabletop.json --case 9  # the sweep
python fuse_live.py --cases nvs_pilot/cases_tabletop.json --case $(seq 0 39) \
    --condition 10 --topk 100 --beta 0 --objscore mean --rank-by instructed \
    --out nvs_pilot/fuse_tabletop_rb.json
python eval_move.py --cases nvs_pilot/cases_tabletop.json --steps 3 \
    --condition 10 --save-stops nvs_pilot/move_stops \
    --out nvs_pilot/move_tabletop.json
```

Staging is replayed, not re-searched: every case stores the occluder pose and a
snapshot of all moveable objects. Four repeats of one case gave identical
occlusion and identical A+C+R ranks; residual noise is ±1 rank from GPU
non-determinism.
