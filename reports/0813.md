# NVS as a viewpoint pointer — 59-task, K=10 run

## Where this is now — read this first

Two experiments live in this repo. They ask the same question and they are NOT
interchangeable.

| | 檔案 | 選點依據 | 狀態 |
|---|---|---|---|
| 1. oracle pointer | `eval_nvs_pointer.py`, `eval_nvs_loop.py` → `nvs_pilot/loop_k10/` | `grounded_rank`, i.e. **THOR 的 GT box** | **結果在本檔案下方，但方法已被取代** |
| 2. fusion pointer | `fuse_live.py` | 你們論文的 map-back fusion，零 GT | **進行中** |

Experiment 1 is what every table below reports. Its pointer reads the ground
truth at decision time — the policy is told which synthesised view is the right
answer, which no robot has at run time. So its numbers are an **upper bound on
a pointer**, not a deployable result, and the nvs-vs-random comparison is not
between equally-informed arms. Everything it measured about staging, occlusion
bands, the case list and the walking loop still stands.

Experiment 2 replaces only the pointer. It runs `../sgg_nvs/lib/fusion/`
`channels.py` — the paper's own code, imported, not reimplemented — over a live
THOR frame plus its synthesised sweep. Channel B only (`beta`, pool=mean,
endpoint gate 0.80, `corr=assign`, `predcond_mode=refpred`), matching
`logs/occlusion_ds4_refpred_assign.log`. As of the first 3-case test: the
assembly self-test passes (`--beta 0` reproduces `sgg_live.predict` 10/10), the
endpoint gate covers 90–99% of pairs at 4–9 speaking views, and 1 of 3 cases
recovered grounding that single-view had missed. **The move-point half is not
built yet** — `fuse_live.py` fuses and scores; it does not walk.

A dead end that is deliberately gone: `SemanticStarMatcher`
(`../sgg_nvs/inference_semantic_anchor_fused_egtr.py`) is a different fusion
from the one the paper uses. It was ported here and deleted. If it reappears,
it is a mistake.

**The question.** A robot is given a referring expression (`Find the book on the
table`). Its own single frame does not contain that triplet grounded on the
instance THOR says was meant. Can a novel-view synthesiser tell it **where to
stand** so that a single real frame does?

**Success is a single REAL frame.** Never a synthesised one. The robot must walk
to a pose and its own camera, at that pose, must produce the class triple with
the subject box on the right instance (IoU >= 0.5 against its VISIBLE box).
Ranking is EGTR's own `max_p(rel) x s_subject x s_object`; the score is `hit@K`.

**The NVS is an oracle.** The 20 lemniscate viewpoints are RENDERED by THOR, not
generated by Stable Virtual Camera. That makes this an upper bound on what a
perfect generator could point at — and it makes a null result attributable, since
a viewpoint that does not exist in the cone is not a generator failure.

**Elevation is discarded.** A lemniscate pose is 3D; the base is not. Only (x, z)
is executed, the body never changes height. Synthesising a viewpoint the robot
cannot occupy is a capability, not a defect; what is measured is whether the
**azimuth component alone** still carries the recovery.

## The pipeline

### Coordinates

AI2-THOR inherits Unity's frame: **left-handed, `y` is up**, so **`x`–`z` is the
horizontal floor plane** and every position is in metres.

```
        y  up
        |
        |        z  (yaw = 0 faces +z)
        |      /
        |    /
        |  /
        +----------- x   (yaw = 90 faces +x)
             floor = the x-z plane
```

| quantity | convention | measured here |
|---|---|---|
| position | `(x, y, z)` metres, `y` up | agent base `y` = 0.903 |
| `yaw` | rotation about `y`; **0° faces +z**, increasing toward +x (clockwise seen from above) | `yaw_towards` = `atan2(Δx, Δz)` |
| `cameraHorizon` (pitch) | **positive = looking DOWN**, clamped to [−30°, +60°] | reference pose 53.0° |
| camera height | read from THOR's `cameraPosition`, not computed | **1.578 m** standing, **0.95 m** crouching |
| navmesh | a set of `(x, z)` points only — 0.25 m grid | — |

**What this means for the sweep.** A lemniscate `azimuth` is a rotation about the
**vertical (`y`) axis through the orbit centre**, so it slides the camera around
within the `x`–`z` plane — that component the base can execute. An `elevation`
raises or lowers the camera **along `y`**, which the base cannot do at all. Worked
example from case 2, view 03:

```
reference camera   y = 1.578    pitch = 53.0°
view 03            y = 1.717    pitch = 61.8°     az +28.5°, el +8.8°
                       ^^^^^                       ^^^^^^^  ^^^^^^^
                       +0.14 m in y                executed  discarded
```

The robot walks to that view's `(x, z)`, stays at `y = 1.578`, and re-aims. So the
**+28.5° of azimuth is reproduced exactly and the +8.8° of elevation is thrown
away** — which is why the report keeps asking whether azimuth alone carries the
recovery.


```
instruction  "Find the book on the table"
     |
     |  THOR is the examiner: it resolves the instruction to a TRIPLET
     |  (book, on, table) and to the one INSTANCE that satisfies it.
     |  The class pair must be unique in view, or the task is dropped.
     v
staging      slide a moveable object already on the same surface into the
             line of sight, on a grid over the tabletop.  Its footprint must
             stay fully on the surface, its box must not intersect the target
             or anything else resting there.  Geometry rejects; occlusion
             only ranks the survivors.
     v
pose_0       the robot stands here, looking at the target
     |
     +---> [ ITERATION k, up to K = 10 ]
     |
     |     1. GRADE  the robot's own frame at pose_k, single view, EGTR
     |               top-100.  Hit = class triple matches AND subject box
     |               is on the right instance (IoU >= 0.5).
     |               hit -> STOP, success at step k
     |
     |     2. SWEEP  20 oracle-NVS views on a lemniscate centred on pose_k
     |               (az = 30 sin t, el = 15 sin 2t), rendered by a THOR
     |               third-party camera.  The robot is parked across the
     |               room first, so its shadow is identical in all 20.
     |               Every view is graded by the same rule as step 1.
     |
     |     3. POINT  among the views that recovered the triplet, take the
     |               best grounded rank that is (a) not within 0.20 m of
     |               anywhere already visited and (b) has a navmesh point
     |               within 0.50 m.
     |               no such view -> fall back to a random bearing
     |
     |     4. WALK   project the chosen viewpoint onto the floor: take its
     |               (x, z), DISCARD its elevation, never change body
     |               height, teleport to the exact coordinate (navmesh snap
     |               only if THOR refuses), then re-aim at the target.
     |
     |     5. REMEASURE  the target's box and the scene graph belong to the
     |               frame now in front of the robot.  Nothing is carried
     |               over from pose_k.
     |
     +---< pose_{k+1};  its frame is BOTH the success test for this step
           AND the reference the next sweep orbits, so an iteration costs
           one extra sweep and nothing else.

STOP when: the frame is graded a hit / the budget K is spent / a move fails.
```

**Why the fallback is a random step rather than an exit.** An arm that stops
early is not comparable to one that keeps moving, so `nvs` keeps its budget by
walking randomly when the sweep is empty. Both arms draw from the **same bearing
sequence**, which makes the degenerate case exact: if every sweep comes up empty,
`nvs` does not merely resemble `random`, it reproduces it step for step. Every
difference between the two arms is therefore attributable to the guided steps,
and a success is credited to NVS only when the step that produced it was guided.


## Configuration

| | |
|---|---|
| trajectory | Gerono lemniscate, 20 views, `az = 30 sin t`, `el = 15 sin 2t` |
| orbit centre | the target's depth along the robot's own optical axis |
| grader | `task_find.grade`, IoU 0.5, top-100, predicate `on` only |
| detector | EGTR finetuned on VG150 (`../sgg_nvs`) |
| tasks | 59 frozen (`nvs_pilot/cases_frozen.json`), 42 floor plans, 51 distinct start poses |
| loop budget | K = 10 moves |
| staged occlusion | aimed at 0.50, capped at 0.90 — median 0.48, max 0.67 |

**Three policies, one grader, the same budget.**

- `stay` — do not move. The no-NVS floor, and the shared origin of the others.
- `random` — move the same distance in a random bearing, re-aim at the target.
- `nvs` — walk to the pose of the best recovering view; when no view recovers
  the triplet, fall back to a random step **drawn from the same bearing
  sequence**, so an all-empty guided run reproduces the random run exactly.

### Reading the tables

| row | what it is | why it is there |
|---|---|---|
| `stay` | the robot does not move; the score is its own starting frame | the **no-NVS floor**, and the shared origin of the other two arms |
| `random` | move the same distance in a random bearing, then re-aim at the target | the control that matters. In a cluttered room almost any sideways move changes what is occluded, so without this the table would measure *"moving helps"* rather than *"the NVS suggestion helps"* |
| `nvs` | walk to the pose of the best recovering view; when no view recovers the triplet, fall back to a random step | the policy under test, **as a policy** — including the steps where it has nothing to point at |
| `nvs (guided win)` | the same arm, but a success only counts when the step that produced it was **guided** | the honest attribution. A success reached on a random fallback step is not NVS's doing |
| `ceiling` | in how many cases **some** novel view recovered the triplet | **not a policy** — an upper bound. It separates *"NVS did not help"* from *"no recovering viewpoint exists in the cone"*, which are different conclusions with different fixes. A pointer can never beat this number |

Both moving arms are handed the target's position to **aim** at. That is a shared
oracle and it is deliberate: the comparison isolates where to **stand**, which is
the only thing NVS is being asked for. Re-aiming is also not optional — reusing a
recorded camera pitch points the agent at the floorboards.

**Strata.** `stratum M` is the cases the robot's own starting frame MISSED, which
is the regime the whole experiment is about. `stratum H` is the cases it already
HAD, kept so that a policy which *breaks* what already worked shows up. `pointer
existed` is the subset where the sweep had somewhere to send the robot — the
head-to-head, since over all cases the `nvs` arm is diluted by the ones where it
declines to move.

**`hit@K`** — the instructed triplet appears within the top `K` of EGTR's own
ranking with its subject box on the right instance. Rank, never score: the top
triplet scores ~0.01 because the ranking is `rel x s_subject x s_object`, and
that product is not comparable between frames.

## Result

`stratum M` — the 53 cases the robot's own starting frame missed:

| policy | @1 | @2 | @3 | @5 | @10 | metres |
|---|---|---|---|---|---|---|
| random | 12 | 16 | 20 | 25 | 27 | 2.60 |
| **nvs** | **18** | **24** | **27** | **30** | **33** | **2.19** |

Two different answers to "does NVS help":

**Success rate — no.** Paired over 53 cases: NVS wins 6, random wins 6, both
succeed 21, both fail 20. **p = 0.61.** Given ten moves, walking randomly finds
it just as often.

**Speed — yes, decisively.** Over the 21 cases both arms solved: median 1 step
vs 3, median 0.53 m vs 0.98 m, and NVS is faster in **12 cases, slower in 0**.
**p = 0.0002.**

So: NVS does not find more, it finds sooner and walks less. Any claim for it has
to be made on the cost axis; on final success rate alone there is nothing.

At K = 3 the paired success-rate test looked favourable (p = 0.063). That was
the budget being too small for the control to catch up, not an effect.

## Two limits

- **201 of 265 sweeps (76%) found no recovering view.** The 27 guided wins came
  from the 64 sweeps that did point somewhere — a high conversion. The
  bottleneck is having something to point at, not acting on it.
- **11 of 59 tasks are unreachable by any viewpoint** — EGTR never emits the
  class triple, in the robot's frame or in any of the 20 synthesised views.

Iteration does open new viewpoints, modestly: of 27 cases whose first sweep was
empty, 11 found a usable view after moving.

| defect | effect |
|---|---|
| `SetObjectPoses` RGB lags its own masks by a frame | the detector was graded on the pre-staging scene |
| a refused move ended the rollout | 5 of 58 arms stopped early with budget unspent; now re-aims up to 6 times |
| amodal reference perturbed the frame it measured | grading now uses the visible box only — measured to change no verdict, and 6x faster |
