# Robot experiments on the NVS-SGG framework

Two experiments have run. They ask the same question — can synthesised views
help a robot act on `find the X behind the Y` — and they are not
interchangeable. This file covers both; the earlier one is kept short because
its method is superseded.

| | motion | pointer / decision | status |
|---|---|---|---|
| 1. oracle pointer | **yes**, up to 10 moves | `grounded_rank`, i.e. THOR's ground-truth box | **superseded** — ground truth inside the control loop |
| 2. A+C+R on an instruction | no | the paper's fusion, no ground truth | **current** |

Nothing yet combines the current fusion with motion. That is the next step and
the reason experiment 1 is still described here at all.

---

# 1. Oracle pointer, with motion (superseded)

59 `on` tasks, K = 10 moves, three policies sharing one grader and one budget:
`stay` (do not move), `random` (same distance, random bearing), `nvs` (walk to
the pose of the best recovering synthesised view; fall back to the SAME random
bearing sequence when no view recovers, so an all-empty guided run reproduces
the random run exactly).

Trajectory: Gerono lemniscate, 20 views, `az = 30 sin t`, `el = 15 sin 2t`,
orbited about the target's depth along the robot's own optical axis. Views 9 and
19 reproduce the input pose and are dropped. Elevation is discarded on
execution — only `(x, z)` is walked, the body never changes height.

## Result — stratum M, the 53 cases the starting frame missed

| policy | @1 | @2 | @3 | @5 | @10 | metres |
|---|---|---|---|---|---|---|
| random | 12 | 16 | 20 | 25 | 27 | 2.60 |
| **nvs** | **18** | **24** | **27** | **30** | **33** | **2.19** |

**Success rate — no effect.** Paired: NVS wins 6, random wins 6, both 21,
neither 20. **p = 0.61.** Given ten moves, walking randomly finds it as often.

**Speed — decisive.** Over the 21 both arms solved: median 1 step vs 3, 0.53 m
vs 0.98 m, NVS faster in **12, slower in 0**. **p = 0.0002.**

So NVS does not find more, it finds sooner. Any claim has to be made on the cost
axis. (At K = 3 the success-rate test looked favourable at p = 0.063; that was
the control not yet having caught up, not an effect.)

**Why it is superseded.** The pointer reads `grounded_rank`, which is computed
against THOR's ground-truth box — the policy is told which synthesised view is
the right answer. No robot has that at run time, so the arms are not equally
informed and the numbers are an upper bound on a pointer, not a result about
one. Everything else it established still stands: the staging, the occlusion
bands, the case list, the walking loop.

**Two limits worth carrying forward.** 201 of 265 sweeps (76%) found no
recovering view at all — the bottleneck was having something to point at, not
acting on it. And 11 of 59 tasks were unreachable by any viewpoint: EGTR never
emitted the class triple, in the robot's frame or in any of the 20 views.

Per-task tables are not reproduced here; they are `nvs_pilot/loop_k10/`
`results.json` joined with `nvs_pilot/cases_frozen.json`.

# 2. A+C+R applied to an instruction, no motion (current)

The fusion the paper ships (`lib/fusion/channels.py`, channels A+C+R) run on a
live THOR frame plus 20 synthesised views, asked an instruction instead of a
benchmark. `fuse_live.py` imports the paper's own functions rather than
reimplementing them, and `--beta 0` reproduces `sgg_live.predict` exactly, which
is checked every run (71/71 passed).

71 cases across 28 floor plans, `Find the bottle behind the plant`, occluder
staged to hide the landmark by a median 36% (band 0.25–0.50).

| | source |
|---|---|
| the two class names and the predicate | **the instruction** |
| which query is the bottle, which is the plant, how strongly they relate | **the model** |
| which bottle is *the* bottle | **ground truth, at grading only** |

Candidates are the top-10 of EGTR's 200 decoder queries by `p(bottle)` × the
top-10 by `p(plant)` — about 100 pairs. Ranked by `p(class)`, not by argmax
class: median `p(class)` on these targets is 0.07, and requiring argmax would
discard most of the detections. The **predicate is not conditioned**: whether
the model says `behind` about that pair is the quantity under test.

**Robot criterion.** The robot scans the ranked list, takes the *first* entry
matching the instruction, and walks there. Success = that entry is the right
instance (`class_rank == grounded_rank`). A right answer sitting below a wrong
one is a failure, because the robot never gets there.

## What is in the list, and the tension it creates

Each candidate PAIR appears once, carrying its own argmax predicate over all 50
— not once per predicate:

```
 1   bottle-plant(A)   near        <- this pair's strongest predicate is `near`
 2   bottle-plant(B)   on
 3   bottle-plant(C)   has
 ...
12   bottle-plant(D)   behind      <- first match; class_rank = 12
```

**A pair whose `behind` score is good but whose `on` score is better never
appears as a `behind` entry at all.** It is listed as `on` and skipped, even if
it is the correct pair.

**Ranking and acceptance disagree.** A pair ranks by `max_p(rel) · s~_i · s~_j`,
i.e. by its STRONGEST predicate, usually `on`; it is then accepted only if that
strongest predicate is `behind`. Observed: `cup has paper`, `pot with plant` —
predicates the THOR export cannot produce, taking the argmax and disqualifying
the pair. Channel V (zero the inadmissible predicates) is the existing lever and
has not been run under this criterion.

## Where each channel acts

| channel | stage | what it does | uses novel views |
|---|---|---|---|
| **A** | the ranking | repairs `s~` from the best matching view (max pool, class gate, cos 0.80) | yes |
| **C** | the scan | merges duplicate detections so one object cannot occupy several entries | **no** |
| **R** | the label | rewrites a pair's predicate from the cross-view consensus, so a pair the reference called `near` can become `behind` and qualify | yes |

A does **not** enter candidate selection — that uses the reference frame's own
class probabilities — so if the right bottle is outside the top 10 by
`p(bottle)`, A cannot rescue it, only reorder what is already there.

## Result

| | robot succeeds | instruction matched at all | @1 / @5 / @10 |
|---|---|---|---|
| single-view | 16/71 (23%) | 54 | 1 / 6 / 11 |
| A | 17/71 (24%) | 54 | 1 / 7 / 11 |
| **A+C+R** | **19/71 (27%)** | **59** | 1 / 9 / 15 |

`@K` means "the robot reads only the first K entries of the CONDITIONED list" —
the ~100 pairs the instruction's class names licensed — so the 27% column is
`@100`, the whole list. **This is not the paper's `R@K`**, which ranks against
every triplet in the scene; being 10th out of 100 pairs already known to be
bottles and plants is a far easier bar.

Paired: single → A+C+R gains 5, loses 2. **Not significant** — a 5-vs-2 sign
test is p ≈ 0.23. The honest reading is "no harm, trend upward", not "it works".
**A is worth +1**; C+R the rest, and R's consensus relabel is why "matched at
all" moves 54 → 59. That is the only place multi-view evidence is visibly doing
something.

## The binding constraint is instance disambiguation, not the relation

The first instruction-matching entry sits at a **median rank of 12** (1–74).
59 of 71 cases have the model saying `bottle behind plant` somewhere; only 19
say it about the right bottle, and `@1` is **1**.

The IoU distribution says the threshold is not the argument: successes have a
median best IoU of **0.83**, failures **0.03**. Failures are not near misses —
the box is on a different object. Only 5 of 40 sit in 0.3–0.5.

## Does fusion help most where the first view is worst?

That is the mechanism's signature, so it is worth splitting:

| landmark occlusion | n | single | A+C+R |
|---|---|---|---|
| 0.25–0.32 | 14 | 3 | 3 |
| 0.32–0.38 | 39 | 12 | **14** |
| 0.38–0.51 | 18 | 1 | 2 |

Single-view drops to **1 of 18 (6%)** in the hardest band, so yes — when the
first view is bad the task is close to unanswerable. But fusion recovers one
case there. The gain sits in the middle band instead. Read one way, the band
0.25–0.50 is too narrow: the easy end leaves fusion no room and the hard end may
already be past saving.

# Three dead ends, all measured

**`on` is the wrong predicate to test a multi-view mechanism on.** It is
viewpoint-INVARIANT; `channels.py` argues only viewpoint-dependent facts can be
informed by a second viewpoint, and ships predCond with `on` excluded. On 59
`on` cases A+C+R moved the answered count 6 → 6.

**Free-form SGDet has no measurable signal here.** On the same 71 `behind`
cases without conditioning, the instructed triplet reached the top-100 in
**1 of 71** — not because the objects are missing: `probe_size.py` finds EGTR
detects and correctly classifies the target in **31 of 71**. The object end is
fine; the triplet loses the ranking to `laptop on table`. Conditioning on the
instruction's class pair is what turned 1 into 59.

**Target size is not the problem.** The graded instance covers a median 0.55% of
the frame and detection does not fall with size (42% under 0.5%, 53% at
0.5–1%). An earlier reading of the task sheets blamed the standoff distance; the
measurement does not support it.

# Limits to carry into any write-up

- **n is 71 across 28 floor plans**, 2.5 tasks per plan sharing a layout and
  often a camera pose. Effective n is below 71 for a sign test. 56 of the 90
  non-bathroom floor plans are still untouched.
- **Not comparable to the paper's SGDet tables.** Conditioning on the class pair
  is a different question asked of the same model.
- **The NVS is an oracle** — 20 views rendered by THOR, not generated by the
  model. This is an upper bound on what a perfect synthesiser would buy.
- **R is ported, not imported** — it is inline in `occlusion_channels.py` rather
  than a function in `channels.py`, so this copy can drift from it.
- Channel **B is off** by request; **D** is not part of A+C+R.

# Reproducing

```
python freeze_cases.py --cases nvs_pilot/cases_wide.json --predicate behind \
    --min-occlusion 0.25 --target-occlusion 0.35 --max-occlusion 0.50 \
    --out nvs_pilot/cases_behind.json
python fuse_live.py --cases nvs_pilot/cases_behind.json --case $(seq 0 70) \
    --topk 100 --condition 10 --out nvs_pilot/fuse_live_cond.json
python show_tasks.py --cases nvs_pilot/cases_behind.json --n 12   # what it asks
python probe_size.py --cases nvs_pilot/cases_behind.json          # detection floor
```

Staging is replayed, not re-searched: every case stores the occluder pose and a
snapshot of all moveable objects. Four repeats of one case gave identical
occlusion and identical A+C+R ranks; residual noise is ±1 rank from GPU
non-determinism.
